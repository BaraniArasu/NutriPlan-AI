PART 1 — WHAT THE APP CURRENTLY DOES (verified against the actual code)
--------------------------------------------------------------------------------

1. AUTHENTICATION & ACCOUNTS
   - Google OAuth sign-in via NextAuth v5, session/account data stored in
     Postgres through the Prisma adapter.
   - Middleware redirects unauthenticated users away from /dashboard to
     /auth/signin with a callbackUrl back to where they were headed.
   - The app works fully for anonymous (logged-out) visitors too — diet plan
     generation does not require an account.

2. ONBOARDING (3 steps + a generating screen)
   - Step 1 — Personal info: name, age, gender, weight, height, optional body
     measurements (chest/waist/hips/arms/thighs), metric/imperial toggle.
   - Step 2 — Goals: target weight, timeline in weeks, activity level, and a
     safety check (getTimelineWarning) that warns when the requested rate of
     weight change exceeds 1–1.5 kg/week and suggests a safer timeline.
   - Step 3 — Location & preferences: city/country (with browser geolocation
     auto-detect via navigator.geolocation), diet type (veg/non-veg/vegan),
     allergies, disliked foods, preferred cuisine, daily budget.
   - Step 4 — Generating screen: loading animation while the plan is built.
   - All onboarding state lives in a Zustand store persisted to localStorage
     (store/onboarding.js), so a refresh mid-flow doesn't lose progress.
   - Server-side validation (lib/utils.js validateProfile) re-checks the
     required fields before generation, independent of client-side checks.

3. AI DIET GENERATION — MULTI-PROVIDER (lib/ai/)
   - Four interchangeable AI providers: Groq (free, default), OpenAI, Google
     Gemini, and Anthropic Claude — switched with a single env var
     (AI_PROVIDER=groq|openai|gemini|anthropic), no code changes required.
   - Each provider has its own per-model tuning: Anthropic uses structured
     JSON-schema output (output_config.format) with effort levels tuned per
     task; OpenAI and Groq use JSON-mode response_format; Gemini uses
     responseMimeType. Per-provider model overrides via GROQ_MODEL,
     OPENAI_MODEL, GEMINI_MODEL, ANTHROPIC_MODEL.
   - generatePlanMeta(profile): computes calorie/macro/water targets and a
     short plan summary from BMI, goal, activity level, etc.
   - generateDayPlan(...): generates one day at a time (7 meal slots — early
     morning, breakfast, mid-morning, lunch, evening, dinner, post-dinner),
     explicitly avoiding foods used in the last 15 items across previous days,
     using local-to-the-user's-city foods and prices in the user's currency.
   - askFoodQuestion(...) / optimizeDietPlan(...): conversational endpoints for
     "what about this specific food" and "help me adjust my whole plan."

4. DIET PLAN VIEWING & INTERACTION (/diet)
   - Day-by-day tabs; only days generated so far are unlocked, next day is
     generated on demand ("Generate Day N" button), up to 7 days total.
   - Per-meal cards: collapsible, show macros, a daily tip banner, and a
     running nutrition summary bar (DietSummaryBar) against the day's target.
   - Quantity adjustment: +/- controls on each food item recompute that food's
     calories/protein/carbs/fat proportionally in real time (client-side only
     — see Part 2, item 6).
   - Food Q&A: a "?" icon on every food item opens a modal (FoodQueryModal)
     that asks the AI a question scoped to that specific food + the user's
     profile/goal.
   - Plan optimizer: a floating button (DietOptimizeButton) for free-form
     questions about the whole plan (cheat meals, swaps, etc.), only shown to
     logged-in users.
   - Anonymous/logged-out gating: logged-out visitors see only the first 2
     meals of a day and a login prompt overlay for the rest; once 7 days are
     generated, logged-out users are also prompted to log in to continue past
     day limits.
   - Plan + profile are held in sessionStorage on the client so the flow
     survives a page refresh within the same tab (but not a closed tab — see
     Part 2, item 8).

5. DASHBOARD (/dashboard, auth required)
   - BMI (calculated + categorized: underweight/normal/overweight/obese),
     current vs. target weight, activity level, days-to-goal projection
     (weekly kg target derived from timeline).
   - "Goal Progress" card — see Part 2, item 5, this currently renders a
     hardcoded bar, not real progress.
   - List of the user's saved diet plans (most recent 10) with an "Active"
     badge, and a one-click "Generate New Diet Plan" entry point.

6. DATA PERSISTENCE (Prisma / Postgres)
   - Models: User, Account, Session, VerificationToken (NextAuth), plus
     UserProfile (1:1 with User), DietPlan (planData stored as JSON, plus
     weekNumber/isActive/notes fields), ChatMessage (role + content + optional
     food context, linked to a DietPlan).
   - Chat history for the food-Q&A flow is persisted per plan for logged-in
     users. (Optimizer chat is not — see Part 2, item 1.)
   - A plan generated anonymously and later claimed by logging in gets its
     full planData saved via a dedicated /api/diet/save endpoint.

7. TECH STACK
   Next.js 14 (App Router) · NextAuth v5 (beta) + Google OAuth + Prisma
   adapter · PostgreSQL via Prisma ORM 5 · Zustand (persisted) · Tailwind CSS +
   Radix UI primitives · Groq SDK / OpenAI SDK / @google/generative-ai /
   @anthropic-ai/sdk behind the lib/ai/ provider switch · react-hot-toast ·
   date-fns · framer-motion · zod.

PART 2 — SPECIFIC ISSUES FOUND DURING THIS REVIEW
(grounded in the actual code — not guesses; verify before fixing, but these
are real, not hypothetical)
--------------------------------------------------------------------------------

1. Optimizer chat isn't saved. app/api/diet/optimize/route.js never writes
   to ChatMessage, unlike app/api/food/query/route.js which does. A logged-in
   user's "optimize my plan" conversation disappears on refresh while their
   food-question conversation doesn't. Inconsistent and almost certainly
   unintended.

2. Diet plans created for already-logged-in users can save empty data.
   app/api/diet/generate/route.js creates a DietPlan row with planData: {}
   when dayNumber === 1 and the user is already logged in, and stores that
   returned planId client-side. Later, app/diet/page.jsx's "save on login"
   effect explicitly skips saving (via the `|| planId` guard) whenever a
   planId is already set — which it now always is for users who started
   logged in. Net effect: users who are logged in from the start of
   onboarding likely end up with a DietPlan row whose planData is
   permanently `{}`, while users who log in mid-flow get the real data saved
   via /api/diet/save. This needs a single, consistent source of truth for
   "when does the full 7-day plan get written to the DB."

3. Dashboard "Goal Progress" bar is hardcoded. In
   components/dashboard/DashboardClient.jsx, the progress fill width is
   `Math.max(5, Math.min(95, 20))` — literally always 20%, regardless of the
   user's actual weight or time elapsed. There is no weight-logging feature
   backing it, so the number is fabricated. Either build real progress
   tracking or remove the visual until there's real data behind it.

4. No rate limiting on AI-calling routes. /api/diet/generate,
   /api/diet/optimize, and /api/food/query all call a paid (or free-tier
   rate-limited) AI provider and are reachable by anonymous users with no
   throttling. This is a real cost/abuse exposure once a paid provider
   (OpenAI/Gemini/Anthropic) is selected via AI_PROVIDER.

5. Quantity adjustments aren't persisted. The +/- quantity controls in
   DietMealCard.jsx only update local component state (`quantities`) — a
   page refresh silently reverts every food back to its AI-generated default
   quantity, with no save-back to sessionStorage, the DB, or even a toast
   warning the user that changes aren't saved.

6. Anonymous plans are lost on tab close. Plan + profile only live in
   sessionStorage, not localStorage, so a logged-out user who closes the tab
   (rather than just refreshing) loses their generated plan with no recovery
   path and no warning that this will happen.

7. README is out of date. It still describes a Gemini/GPT-4o-only setup,
   references .ts/.tsx files that don't exist in this codebase (it's .js/
   .jsx throughout), and predates the lib/ai/ multi-provider system entirely.
   It should reflect the actual current architecture.

8. weekNumber exists but is unused. DietPlan.weekNumber is always 1 with no
   code path that increments it or offers "continue to week 2" — either wire
   it up or drop it from the mental model of the schema.

9. No automated tests. There is no test runner, no unit tests for the
   AI-provider JSON parsing/validation, and no coverage for the profile
   validation logic — the kind of code most likely to silently break when
   models or prompts change.
